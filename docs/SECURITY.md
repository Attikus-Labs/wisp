# Wisp — Security Notes & Threat Model

Wisp is a clipboard manager, which means it sees everything you copy. That makes
its security posture the most important thing about it. This document describes
what Wisp does to earn that trust, what it deliberately does *not* do, and the
trade-offs involved.

## Design principles

1. **Record everything — leak nothing.** Wisp keeps a *complete* clipboard
   history, secrets included, so what you copied is always there when you need it.
   The guarantee isn't that Wisp avoids *seeing* secrets — it's that secrets can't
   *escape*: memory-only, no disk, no network, output-only, screen-capture-excluded.
2. **Don't persist.** What isn't stored can't be stolen. History is memory-only.
3. **Don't phone home.** No network code means nothing can be exfiltrated.
4. **Don't depend on strangers.** Zero third-party packages — no transitive
   supply chain.
5. **Ask for as little as possible.** One optional permission, for one purpose.

## What gets recorded — and what doesn't

Wisp records **everything you copy** — plain text from any app, including
usernames, passwords, and one-time codes from password managers. This is
deliberate: a clipboard history with holes in it isn't a clipboard history. There
is **no content filter and no app denylist**.

The *only* thing Wisp skips is its **own paste output**. When you paste an entry,
Wisp puts it back on the system pasteboard to deliver it; re-recording that echo
would overwrite the entry's captured formatting with a text-only copy. Wisp stamps
its pastes with a private marker (`com.brinas.wisp.self-paste`) and skips exactly
those — see [`PrivacyFilter`](../Sources/WispCore/PrivacyFilter.swift). As a
courtesy it also stamps the [nspasteboard.org](https://nspasteboard.org)
`AutoGeneratedType` and `ConcealedType` markers on that echo, so any *other*
clipboard manager you happen to run skips it too.

The canonical content is always **plain text**; images and files are never read or
retained. Wisp also keeps the source app's **HTML** representation **in memory** so a
formatted paste (`⌥⏎`) can reproduce the original formatting — never written to disk,
and never parsed by Wisp (it is re-emitted verbatim on paste; the HTML→RTF conversion
that *would* invoke a network-capable importer runs only on Wisp's own synthesized
Markdown, never on captured source HTML).

Because Wisp now holds secrets, the rest of this document is the important part:
**how those secrets are contained, and the residual risks that remain.**

## Containing what we record

Once a secret is in Wisp's history, these properties keep it from escaping:

- **Memory-only.** History is a plain in-RAM array ([`ClipboardHistory`](../Sources/WispCore/ClipboardHistory.swift));
  `ClipboardItem` conforms to no serialization protocol. There is no database, cache,
  temp file, or log of clipboard contents — `UserDefaults` holds *preferences* only.
  Quit Wisp or reboot and the only copy is gone. (See *Data lifecycle*.)
- **No network.** No networking code, no network entitlement, zero dependencies —
  nothing can be exfiltrated. (See *Network*.)
- **Output-only input.** Wisp synthesizes ⌘V to paste and registers a Carbon hotkey,
  but installs **no event tap, global monitor, or Accessibility observer** — it never
  reads your keystrokes or other apps' contents. (See *Permissions*.)
- **Hardened Runtime, no `get-task-allow`.** Empty entitlements + Hardened Runtime
  block a debugger / `ptrace` from attaching and reading Wisp's memory.
- **Excluded from screen capture.** The bezel and search HUD set `NSWindow.sharingType
  = .none` ([`BezelPanel`](../Sources/WispCore/BezelPanel.swift)), so screenshots,
  screen recordings, and screen sharing don't capture on-screen clip text. (Wisp shows
  clip text in the clear in its own window — see the on-screen residual risk below. It
  doesn't try to mask secrets, because 1Password and the like tag usernames and
  passwords identically, leaving nothing to reliably tell a secret from a non-secret.)
- **Optional post-paste auto-clear.** The menu's *Clear Clipboard After Paste*
  (Never / 10s / 30s, default Never) wipes the system pasteboard after a paste — only
  if nothing else has touched it since — to shrink the shared-clipboard window below.

## Residual risks — what Wisp can't fully prevent

Honesty matters more than marketing here. Recording secrets means some surfaces are
**inherent to macOS** and can be mitigated but not eliminated. If your threat model
includes a hostile process already running on your Mac, weigh these:

- **The system pasteboard is shared.** To paste, Wisp must place the text on
  `NSPasteboard.general`, where it stays until the next clipboard event — and *any*
  app (or another clipboard manager, or Universal Clipboard) can read it there. The
  `ConcealedType`/`AutoGeneratedType` markers Wisp sets are **advisory only**; a
  hostile or careless app ignores them. This is how clipboard pasting works on macOS,
  not a Wisp bug. The optional *Clear Clipboard After Paste* setting *shrinks* this
  window but can't close it (a copy the target app makes during the delay, or a crash
  before the timer fires, still leaves an opening).
- **On-screen display is visible.** Wisp shows clip text — secrets included — in the
  clear in the bezel and search HUD, by design (you have to see what you're pasting, and
  there's no reliable way to tell a password from a username to mask just one). The
  window is excluded from screen capture (`sharingType = .none`), so screenshots and
  recordings don't catch it — but anyone looking over your shoulder or pointing a camera
  at the screen can read it. Quitting Wisp, *Clear History*, or the auto-clear all remove
  it from view.
- **Memory isn't reliably zeroed.** Swift `String` is immutable/copy-on-write; secrets
  held by Wisp — and transient copies made by AppKit, text fields, and the pasteboard —
  aren't overwritten on deallocation. Freed heap stays readable **in-process** until
  reused or exit. Hardened Runtime blocks *external* inspection, so this is only
  reachable by code already inside Wisp's process.
- **Other clipboard tools & sync.** Maccy/Alfred/Raycast or Universal Clipboard /
  Handoff read the system pasteboard independently and may persist or sync your copies
  — entirely outside Wisp's control.
- **Swap encryption is a system setting.** RAM can be paged to swap; macOS encrypts
  swap by default (and with FileVault on), but if you've disabled that, in-memory
  secrets could theoretically reach disk via paging — a configuration Wisp can't control.
- **Accessibility & no sandbox.** Auto-paste requires synthesizing ⌘V into other apps,
  which the App Sandbox forbids — so Wisp is unsandboxed (like every auto-pasting
  clipboard manager) and the optional Accessibility grant is coarse. The compensating
  controls are Hardened Runtime, Developer ID signing + notarization, empty
  entitlements, and open source (output-only, auditable).

## Memory budget

Because the history lives only in RAM, its size is bounded so a few huge copies can't
balloon Wisp's footprint — and both bounds are user-controlled in the menu:

- **Entry count** — the ring holds 10 / 20 / 40 / 80 entries (default 40).
- **Per-clip size cap** — a byte budget applied to **every field retained: the plain
  text *and* the captured HTML**. Default **2 MB**; selectable as 1 / 2 / 5 / 10 / 50 MB
  or *Unlimited* ([`ClipboardMonitor`](../Sources/WispCore/ClipboardMonitor.swift),
  [`Settings.maxClipBytes`](../Sources/WispCore/Settings.swift)). A clip whose **text**
  exceeds the cap is **not recorded** (it remains on the system pasteboard, so a manual
  `⌘V` still works); **HTML** over the cap is dropped while the text is kept. Worst-case
  retained memory is therefore ≈ *entry count × per-clip cap* — a number you choose.

## Data lifecycle

- History is an in-memory ring of at most 40 entries (configurable 10–80), newest
  first, held by [`ClipboardHistory`](../Sources/WispCore/ClipboardHistory.swift),
  with each entry bounded by the per-clip size cap above.
- **Nothing is written to disk.** There is no database, no cache, no log of
  clipboard contents. The only things persisted via `UserDefaults` are your
  *preferences* — history size, max clip size, arrow direction, keep-formatting —
  never any clipboard text.
- Quitting Wisp or restarting your Mac wipes the history. "Clear History" in the
  menu wipes it immediately.

## Network

Wisp contains **no networking code** and ships with **no network entitlement**.
It runs no in-app update check, sends no analytics, and never syncs. The menu's
**Check for Updates…** simply opens this repository's GitHub releases page in
your browser — *Wisp itself* makes no network request; the browser does. Updates
are delivered out-of-band via Homebrew / GitHub Releases, so the running app
never needs the network. You can verify this — grep the source for `URLSession`,
`Network`, `socket`; there are none.

## Permissions

| Permission | Used for | Required? |
|---|---|---|
| **Accessibility** (TCC) | Synthesizing ⌘V to paste into the previously-active app | Optional — without it, the clip is still placed on the clipboard for a manual ⌘V |

The global ⌘⇧V hotkey uses Carbon's `RegisterEventHotKey`, which needs **no**
permission and is **not** a global event tap / key logger. Wisp never observes
your keystrokes.

## Why Wisp is not App-Sandboxed

A clipboard manager that pastes for you must synthesize a ⌘V key event into
*another* application. The macOS App Sandbox forbids this. Every auto-pasting
clipboard manager (Maccy included) is therefore unsandboxed. Wisp compensates
with:

- **Hardened Runtime** (enabled at signing via `codesign --options runtime`).
- **Developer ID signing + Apple notarization** for release builds.
- **No entitlements requested** beyond the defaults (see
  [`Wisp.entitlements`](../Resources/Wisp.entitlements)).
- **Open source**, so the unsandboxed code is fully auditable.

If you prefer a sandboxed, copy-only build (no auto-paste, no Accessibility),
that's a reasonable fork — the paste path is isolated in
[`Paster.swift`](../Sources/WispCore/Paster.swift).

## Code signing & notarization

Release artifacts produced by `.github/workflows/release.yml` are signed with a
Developer ID Application certificate and notarized by Apple, then stapled. The
workflow publishes a `SHA256SUMS.txt` alongside the `.dmg` so downloads can be
verified:

```sh
shasum -a 256 -c SHA256SUMS.txt
```

## Hardening roadmap

- A CI guard that fails the build if a keylogging (`CGEventTapCreate`,
  `addGlobalMonitor`), network (`URLSession`, sockets), or disk-persistence
  (`Codable` on `ClipboardItem`, `NSKeyedArchiver`, `Data.write`) API is ever
  introduced — locking in the no-keylog / no-network / no-disk guarantees.
- Move the package to Swift 6 strict-concurrency language mode (`.v6`).
- Reproducible builds + published build provenance.

## Reporting a vulnerability

Please open a private security advisory on GitHub, or email the maintainer
listed on the project page. Do not file public issues for security reports.
